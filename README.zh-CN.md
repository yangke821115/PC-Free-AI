# PC-Free AI

**把完整的 AI 智能体装进手机。不需要电脑，不需要服务器——一台装了 Termux 的手机就够。完整 shell、文件读写、SSH、工具调用、多 Agent 协作。数据留在自己设备上，唯一开销是模型订阅。**

> 数据都在自己手机上，除了模型，其他都免费。

**作者**：yangke821115 ｜ **时间**：2026 年 11 月
**环境**：Redmi · Android 17 · [F-Droid 版 Termux](https://f-droid.org/packages/com.termux/) · Kai9000（仓库是 [SimonSchubert/Kai](https://github.com/SimonSchubert/Kai)，1,355 星，带持久记忆的 AI 助手）

## 它到底能干什么

- **读写手机上的真实文件**，不是聊天框里的附件
- **执行 shell 命令**（跑在 proot Alpine 沙箱里，有独立的包管理器与文件系统）
- **SSH 出去**，把手机当指挥中心、服务器当执行器
- **完整走完开发链路**：写代码 → 编译 → 打包 → 签名 → 装机，全程手机不借电脑
- **多 Agent 协作**，接任意 OpenAI 兼容端点，不被单一厂商锁死

一句话：**它对你的整个数字环境有行动能力，而不只是一个对话框。**

## 快速判断这个方案适不适合你

| 你的情况 | 合不合适 |
|---|---|
| 大量时间不在电脑前，但脑子里全是待办 | ✅ 正合适 |
| 想低成本跑自动化的个人开发者 | ✅ 正合适 |
| **需要公网回调接收外部推送**（如平台 Webhook） | ⚠️ 手机做不了，得加一台有公网 IP 的机器 |
| 需要 24 小时不间断、且要求秒级准时 | ⚠️ 后台任务会受系统调度影响 |

## 一、先说清楚我在解决什么问题

### 1.1 场景:AI 得能跟着我走

现在大部分人用 AI 的方式是:坐在电脑前,打开网页或 IDE,问问题,等回答。

这套流程没问题,但它有一个隐含前提——**你得在电脑前**。

我的实际情况是:一天里有大量时间不在电脑前。等车、走路、在床上、在工厂现场。这些时候脑子里的想法和待办事项一样多,但电脑不在手边。

所以我一直在找一个东西:**能在手机上独立运行、能真正干活的 AI**。

不是那种"手机端聊天客户端"——那些只是把请求转发到云端,它对你手机上的东西一无所知。我要的是能读文件、能执行命令、能部署服务、能改代码的那种。

### 1.2 但还有个前提:成本

这一点很少有人在评测里提,但它决定了方案能不能持续。

**整套东西跑下来,现阶段真正要花钱的地方只有一处:大模型订阅。**

| 环节 | 跑在哪 | 成本 |
|---|---|---|
| 大模型 | 云端 | **唯一支出** |
| 手机端 Kai9000 | 我自己的手机 | 0 |
| 电脑端 opencode | 我自己的电脑 | 0 |
| 消息中转 | 飞书 | 0 |
| 常驻任务 | 我自己的手机 | 0 |

手机和电脑都是现成的硬件,不额外买。消息中转用现成的工具。常驻任务也不一定要服务器——后面会讲到,手机上开好自启动和电池策略,一样能长时间稳定跑。

### 1.3 最终目标:连模型订阅也省掉

现在的支出里,模型订阅占全部。但它也不是非花不可的。

我真正想去的终点是:**随着手机和笔记本芯片越来越强,在本地就能跑一个具备 vibe coding 和工具调用能力的开源模型——到那时,模型订阅也不用了。**

现在还没到,但方向是清楚的:

```
现在:  手机(Kai) + 电脑(opencode) + 云端模型(订阅)
       ↓ 芯片变强、开源模型变小
未来:  本地跑开源模型 + 本地 Agent
       订阅 = 不需要,总支出 = 0
```

**这篇文章写的,是过渡期的方案。**

## 二、Kai9000 到底强在哪

我不想写那种"功能列表"式的评测,太虚。我用一天的真实工作来说明。

### 2.1 它能独立部署在手机上

这件事听起来理所当然,其实不是。

大部分声称"支持移动端"的 AI 产品,本质是:
- 网页套壳(手机浏览器打开)
- 云端会话同步(算力在服务器)
- 或者干脆就是个 API 客户端

**它们都不能在手机上"做事",只能"说事"。**

Kai9000 是真正的本地应用。它能:
- 读写手机上的文件
- 执行 shell 命令(通过 Termux)
- 发起网络请求
- SSH 到远程服务器

这意味着它对你的**整个数字环境**有行动能力,而不只是一个对话框。

### 2.2 它可以 vibe coding

这一点是我最意外的。

我原本以为手机只能做"轻量"的事——查资料、写短文、发消息。实际测试下来,**完整的开发流程可以在手机上跑完**:写代码、编译、打包、签名、安装。

举个真实例子:我让它做一个 Android 应用。它做了这些事:

| 步骤 | 它做了什么 |
|---|---|
| 写代码 | 用 Java 写了一个带界面的 Activity |
| 画图标 | 用 Python 生成 5 种尺寸的 PNG 图标 |
| 编译 | 调用 `javac` 编译 Java(还要先解决 JDK 类库路径问题) |
| 打包 | 用 `aapt2` 编译资源、`d8` 生成 dex、zip 组装 |
| 签名 | 用 `zipalign` 对齐、`apksigner` 做 v2/v3 签名 |
| 装机 | 把 APK 放到共享目录,提示我安装 |

**这条链路里没有一步需要电脑。**

而且它不是"告诉我该怎么做"——它是**自己执行**。我只需要在关键节点说"继续"或者"换个方向"。

### 2.3 它能 SSH 连接到服务器

这一点给了它"分身"的能力。

我的手机性能有限,但它能连到一台 2 核 4G 的云服务器上,调用那边的算力、磁盘、常驻进程。

于是形成了一个分工:

```
手机 (Kai)  = 指挥中心
    ↓ SSH
云服务器    = 执行器 + 存储
```

**手机负责"想"和"决定",服务器负责"跑"和"存"。** 这套架构让一台普通手机获得了接近桌面工作站的能力。

需要说明的是:**这不是必需品**。后面会讲到,大部分活儿手机自己能扛,而且在成本上我推荐先别买服务器。但"能 SSH 出去"这个能力本身,让手机的上限不再是手机的上限。

### 2.4 它能替你部署仓库、安装环境、调试应用

这是最实用的一条。

举几个我实际做过的事:

- 把一个 Python 服务部署到服务器上,配好 systemd 单元,设置成开机自启
- 在手机上装好完整的 Android 开发工具链(javac / d8 / aapt2 / apksigner / apktool)
- 排查一个服务为什么起不来(最后发现是数据库被锁,不是权限问题)

**这些事情如果你自己查文档做,每件都要几十分钟到几小时。** 让它在手机上做,你只需要描述目标,然后看着它一步步完成、在出错时自己调整方向。

注意最后一件事的性质——**它不是"按步骤执行",它是"诊断"**。给它一个"起不来"的现象,它自己去翻日志、查进程、试各种可能,最后定位到根因。这已经超出了"代码助手"的范畴。

### 2.5 它支持自定义模型、Skills、MCP

这几点保证了它不会被某个厂商绑死:

- **自定义模型**:接任意 OpenAI 兼容端点。你可以用免费的、付费的、本地的,随时切换。
- **Skills**:把重复性的工作固化成技能,不用每次重新解释。
- **MCP**:标准化的工具协议,能接入外部服务。

它的能力不是产品方决定的,是**你自己配置决定的**。

## 三、说句实话:现在这个赛道的竞争已经很激烈了

如果我几个月前写这篇文章,可以说"手机上的 AI Agent 几乎没得选"。但现在不行了。

### 3.1 现在市面上有什么

先说清楚**事实**。这些是我写作时能查到的公开信息,不是猜的。

**Grok Bot(xAI)**——2026 年 8 月 11 日发布 beta。官方描述是"一支常驻在线的智能体团队":每个 Bot 有**自己的一台云端电脑**(带浏览器、文件系统、终端),7×24 运行,你关掉手机它照样干活。它可以直接操作网页界面,不需要对方提供 API。2026 年 9 月 2 日上了 Android。

**Muse(Meta)**——个人 AI 智能体,手机、桌面都能用。官方 FAQ 说得很清楚:免费但有使用额度,超了可以付费升级;**关掉 App 它仍在后台继续工作**;执行敏感操作前会向你请求批准。

**这两个产品做得比我这套好,这是实话。** 模型更强、界面精致、有专门的工程团队在打磨。我不会假装看不到这一点。

### 3.2 但它们的架构和我不一样

看到这里你可能发现了——**上面这两个产品,手机都只是遥控器。**

真正的执行发生在**厂商的云上**。你的手机负责下指令、看进度、点批准。活儿是在别人的机房里干的。

这不是缺点,反而是它们能做好的原因(云端机器比手机强得多,而且永远在线)。但它带来三个你必须接受的前提:

**前提一:你的工作跑在别人的机器上。**

你的文件、你的操作、你的业务流程,都要经过它。厂商给了权限控制、给了批准环节,这些做得不错。但"要不要把我的业务跑在别人家"这个问题,答案取决于你的工作性质。

**前提二:必须持续订阅。**

Grok Bot 的公开信息写得很明确:需要 SuperGrok、SuperGrok Plus、SuperGrok Heavy,或者 Cursor Pro / Pro+ / Ultra 等订阅档位才能使用。

这个定价逻辑是合理的——**它按"人/月"收费,因为模型成本由厂商承担**。但这同时意味着:厂商没有动机让你换更便宜的模型,你也没有这个选项。

**Muse 是免费带额度的**,这一点要公平地说。但免费额度用完就得升级或等刷新,对重度使用来说这不是可持续的方案。

**前提三:不能换模型。**

这一条我没有找到任何一个支持"自定义 OpenAI 兼容端点"的官方说明。

原因不难理解:**它的商业模式就是"订阅 + 自家模型"**。如果允许你接第三方端点,这个模式就不成立了。所以这不是"暂时没做",是结构上不会做。

| | 厂商 Agent(Grok Bot / Muse) | 自己搭(本文方案) |
|---|---|---|
| 执行在哪 | **厂商的云** | **你自己的手机** |
| 手机的角色 | 遥控器 | 执行本体 |
| 模型 | 绑定自家 | 任意 OpenAI 兼容端点 |
| 计费 | 订阅(人/月) | 按你自己接的端点算 |
| 断网/欠费 | 服务停止 | 你自己决定 |

### 3.3 还有一条绕不过去的:地域

这是最现实的问题,而且和你的技术能力无关。

**这些服务不在中国大陆提供。** 要用就得绕过网络限制——而这么做**违反服务条款**。

后果是具体的:

- 账号随时可能被封,**没有申诉渠道**
- 一旦被封,之前积累的会话、配置、工作流**全部归零**
- 维持"能用"这件事本身,变成一项持续的成本

**这不是技术问题,是可持续性问题。** 一个你每天都要依赖的工具,如果它的可用性建立在"没被发现"之上,它就不适合承担正经业务。

对做外贸的人来说这一点尤其关键:**你的客户在全世界,你的工具却要赌账号不被封。**

### 3.4 所以真正的分水岭在哪

我说了这么多,其实就想指出一个区别——**这个区别和技术好坏无关,和架构有关:**

```
厂商 Agent:  你的手机 ──→ 厂商的云(执行)  ──→ 结果回传
                 遥控器          别人的机器

本文方案:    你的手机(执行)  ──→ 需要时再连别的机器
                 本体              可选
```

**前者是"租一台电脑让 AI 用",后者是"让 AI 住进你已有的设备"。**

这两种模式都能干活。但当你的目标包括**降低成本**和**最终不依赖任何订阅**的时候,只有后者走得通——因为租来的电脑,永远不可能变成你的。

### 3.5 所以我的判断

**如果你的情况和我不同**——在服务可及的地区、预算能接受月费、工作内容可以放在别人云上——**那就用现成的产品。它们确实做得更好,没必要自己折腾。**

**如果你的情况像这样:**
- 需要控制成本,不想被月费绑住
- 需要模型可换(哪天有更好的、更便宜的、更隐私的)
- 需要一个不会因为账号问题突然消失的工具
- 想的是"最终能不能完全自己跑",不是一个更省事的现在

**那自己搭这套是值的。** 本文写的是第二条路。

> **关于本节的事实来源与限度**
>
> 上面关于 Grok Bot 和 Muse 的描述,来自它们各自的官方公告和官方 FAQ。**产品数据和定价会变,请以其最新官方页面为准。**
>
> 我**没有**逐一实测这些产品——我的网络环境访问不了其中一部分,也没法注册。
>
> 关于"不能自定义模型"这一点,我的依据是:**没有找到任何官方说明支持该功能,且这与它们的订阅制商业模式相冲突**。这是**推断**,不是查到明文写着"不支持"。**如果你知道某家已经开放了自定义端点,请指出,这一节我会改。**
>
> 这一节真正想说的,不是"这些产品不好"——它们很好。而是:**架构决定了你能控制什么、不能控制什么。**

## 四、它和 opencode 有什么区别

这是我被问得最多的问题:**这俩不是重复了吗?**

不重复。它们是**两种不同的东西**,各自解决不同的问题。

### 4.1 一句话区别

| | Kai9000 | opencode |
|---|---|---|
| 形态 | **完整应用**(带 GUI) | **终端 Agent**(CLI/TUI) |
| 主战场 | 手机 | 电脑 |
| 交互 | 点、滑、拍照、分享 | 键盘、终端 |
| 强项 | 随时随地、低门槛 | 大仓库、长任务、并行 |

**打个比方:Kai 是随身携带的工具刀,opencode 是车间里的数控机床。** 你不会拿机床去拆快递,也不会拿刀去铣零件。

### 4.2 具体差异

**1. 输入方式决定使用场景**

Kai 有原生的手机界面:语音、拍照、分享菜单、剪贴板。你在工厂现场拍一张设备铭牌,直接就能问它这是什么型号。opencode 在终端里,这些事都做不到。

**2. 运行环境决定能力上限**

opencode 跑在电脑上,有完整的 Docker、足够的内存、稳定的电源。它能开沙箱、跑编译、索引大仓库、同时开好几个子 Agent。

Kai 跑在手机上,这些都没有。Android 会在内存紧张时把它的进程回收掉,后台任务会被系统限流。

**3. 定位决定它该做什么**

我现在的分工是:

```
手机 (Kai)      → 随时查看、快速决策、完整开发流程、拍照识别、语音输入、定时轮询
电脑 (opencode) → 大重构、多 Agent 并行、长时间调试、跑测试
```

**Kai 负责"在场",opencode 负责"深度"。**

### 4.3 先把话说清楚:我不是在说 opencode 不好

这一节很容易被读成"Kai 赢了 opencode"。**完全不是这个意思,得说明白。**

**opencode 是为终端设计的,而在终端里它非常强。** 上面列的那些"Kai 有、它没有"的东西,反过来看就是"它有、我没有":

- **子 Agent 并行** —— 我真没有,我羡慕
- **工具调用无上限** —— 它有,我有 15 次硬编码
- **真正的容器隔离** —— 它有 Docker,我只有 proot 的用户态重定向
- **大仓库索引、长时间调试** —— 它扛得住,我会拖

**这些不是我在"宽容"它,是我确实没有、也确实想要的东西。**

拿它来对比,唯一目的是**说清楚这套方案适合谁**,不是给谁打分。而且结论可能是反的:

> **如果你手边有电脑、也习惯终端,那 opencode 很可能就是更适合你的工具,不用折腾手机这一套。**
>
> **本文写的是"没有终端的那几个小时"该怎么办。**

我两个都在用,一天里会来回切换。**文章最后那一节讲的正是一座桥——桥只有在两头都站得住的时候才有意义。**

### 4.4 一个正在发生的变化:opencode 也在往手机上走

**这一段要反过来读:它证明了 opencode 的可移植性,不是它的短板。**

一个项目能在完全没设计过的平台上跑起来,前提是它的架构本身够干净——逻辑和界面分得开、依赖能替换、没有绑定某个操作系统的私有接口。**能做到这一点的项目不多。**

有意思的是,opencode 社区正在把这件事补上。目前有三条路:

**路一:官方方案 —— `opencode serve` + 自带 Web UI**

电脑上起服务,手机浏览器打开,可以「添加到主屏幕」当 App 用。

**零第三方组件,最稳。** 前提是手机和电脑在同一局域网,或者做了内网穿透。

**路二:在手机上直接跑 opencode 本体**

有社区项目把 opencode 交叉编译到了 Android:

| 项目 | 说明 |
|---|---|
| `guysoft/opencode-termux` | 交叉编译 Bun + WebKit,v1 稳定 / v2 预发布 |
| `bd-loser/opencode-bionic` | 一条命令装机,stable/dev 双通道 |

注意:**这两条是"在手机上装 opencode 本体",不是遥控器。**

**路三:手机遥控电脑上的 opencode**

| 项目 | 状态 | 说明 |
|---|---|---|
| `dzianisv/opencode-mobile` | 活跃 | 开源安卓客户端 |
| `crim50n/oc-remote` | 活跃 | Kotlin 原生,专连 OpenCode server |
| `doza62/opencode-mobile` | 已停更 | React Native 客户端 |
| `Eslamasabry/opencode-mobile-next` | 活跃 | 本地跑 + 远程指挥两用 |

另外还有一批通用的多 Agent 编排平台(如 `orca`、`paseo`、`claudecodeui`),也能管 opencode,但它们是为"管理一群 Agent"设计的整套系统。**为了一个功能背一整套系统,不值。**

> 以上项目数据为 2026 年 11 月查询所得,会随时间变化。

### 4.5 那我为什么还用 Kai?

因为**它开箱即用**。

上面那些方案,不管是自建服务、交叉编译还是遥控客户端,都需要你先配置、先调试、先解决一堆环境问题。

**Kai9000 装上就能用。** 对"随时掏出来干点事"这个需求,低摩擦比功能多更重要。

## 五、手机能跑 opencode 本体吗?满血还是残血?

这是个好问题,答案是**分两层看**。

### 5.1 软件层:基本是满血的

前面提到的两个安卓移植项目,都是**打包工程,不改 opencode 的逻辑**。

所以装上去的是同一个 opencode —— 工具调用、会话管理、多 Agent、MCP、插件,功能集是一样的。**不是阉割版。**

差别只在**引擎版本**:
- `guysoft` 的 v1 用的是打过补丁的 Bun 1.2.13(旧一些)
- v2 和 `bd-loser` 用的是官方 Bun 1.4.2 的安卓目标(更接近上游)

### 5.2 环境层:真正被削掉的是什么

真正打折扣的不是程序,是**操作系统提供的地基**。但有些差距正在快速缩小:

| 能力 | 手机上的 Android 移植版 | 电脑上的 opencode | 我实际用过的 Kai |
|---|---|---|---|
| 工具调用(读文件、跑命令) | ✅ 一样 | ✅ | ✅ 一样 |
| MCP / 插件 | ⚠️ 理论可用,实测看包 | ✅ | ✅ 支持 |
| **沙箱环境** | ❌ 无 proot/容器 | ✅ Docker | ✅ **有 proot Alpine 沙箱**(见下) |
| 编译、跑测试、大仓库索引 | ⚠️ 明显慢 | ✅ | ✅ 能跑,超大仓库会拖 |
| 后台长时间跑 | ⚠️ 要唤醒锁,否则被杀 | ✅ | ✅ 开了电池无限制后稳定 |
| 屏幕和输入 | ⚠️ 终端小屏,打字费劲 | ✅ | ✅ 见第七节,输入方式其实更多 |
| **内存** | ⚠️ 看机型 | ✅ | ✅ **16GB 起,可扩展** |

**一句话:程序是满的,机器不是——但"机器"这一块,这两年进步得比大多数人以为的快。**

#### 关于沙箱

手机上是**有沙箱的**,只是形式和电脑不太一样。

我用的是 **proot 装的 Alpine Linux**——有自己的包管理器、自己的文件系统、自己的进程树,和宿主的 Android 系统隔开。

写这段文字的时候,我就跑在这样一个沙箱里:读它的内存占用、查它的磁盘空间、在里面装工具链、跑脚本、改文件。

它和 Docker 的差别在**隔离强度**:proot 是用户态的**文件系统重定向**,不是内核级隔离,所以跑不了需要特权的操作(装内核模块、操作真实网卡、Docker-in-Docker)。

**但对"隔离出一套干净的开发环境"这个需求,它完全够用。**

#### 关于内存

**跑 Kai9000 的那台红米 K90 MAX 是 16GB 内存**,而安卓有内存扩展功能,可以再挂 16GB,合起来 **32GB**。市面上已经有 24GB 的机型,加扩展能到 **48GB**。

**48GB 是什么概念——比大多数开发者的台式机还多。**

这改变了一些判断:

- **大仓库索引**:十几个 G 的项目放得下,不会频繁换页
- **并行跑多个任务**:每个进程有自己的地址空间,不再是奢侈品
- **将来本地跑模型**:虽然现在还没到,但这个内存量已经能容纳中小尺寸的模型

我实测当前这台机器的沙箱:**15.6 GB 内存、8 核、109 GB 可用磁盘**。这就是一台中端笔记本的配置。

**所以"手机内存不够"这个说法,该更新了。它曾经是真的,现在不是。**

下一步的瓶颈会转移到**散热和持续功耗**,不是容量——那是另一个话题。


### 5.3 还有个容易忽略的点:原生依赖

opencode 背后依赖一堆原生库(SQLite、ripgrep、tree-sitter 之类)。

这两个移植项目为了让它跑起来,专门处理了安卓的 seccomp 限制、bionic 架构、WebKit 引擎——**说明这条路本身是有摩擦的**。

打包时预编译了大部分,但个别功能可能因为缺某个预编译产物而降级。具体哪个降级,得装了才知道。

### 5.4 那到底什么算"手机干不了"

这是最容易说滑的地方。我说"手机不能干正经工程活",听起来像是"手机只能玩玩"——**这不符合事实,也不符合我自己的经历。**

所以先把"工程"这个词定义清楚。**我把它分四档:**

| 档位 | 典型项目 | 手机能不能干 |
|---|---|---|
| **一、写脚本、改配置、调接口** | 几十到几千行,单文件或小仓库 | ✅ 完全够,和电脑没区别 |
| **二、完整应用开发** | 中小型 App / 服务,有构建流程、有测试 | ✅ 能,我这一年基本都这么干 |
| **三、中大型系统维护** | 多服务、多容器、线上排障 | ⚠️ 能,但要 SSH 借外部算力 |
| **四、从零造一个大型软件** | 操作系统内核、浏览器引擎、3A 游戏、大型 IDE | ❌ 干不了,这是另一回事 |

**关键在第三档和第四档之间那条线在哪。**

第三档——**我在手机上实际做过的事,可以当参照:**

- 完整重建一套 Android 应用(从反编译、读 smali、改逻辑,到用 javac / d8 / aapt2 / apksigner 重新打包签名)
- 排查一个跑不起来的生产服务,最后定位到是数据库被事务锁住,不是权限问题
- 部署服务、配 systemd、设置开机自启、跑定时任务
- 改代码、提交、推送到远端仓库

**这些放在任何一个标准里,都算"正经工程活"。而它们全部是在手机上完成的。**

**真正干不了的,是第四档:**

不是说手机跑不动,是**条件根本不成立**:

- **大型编译**:一个现代浏览器的完整构建要几十小时、上百 G 磁盘、几十 G 内存。手机不是慢一点,是差两个数量级
- **大规模并行编译/测试**:需要几十个核同时跑,手机只有 8 个,还要分给系统
- **需要 GPU 的开发**:着色器编译、模型训练、图形调试——手机 GPU 驱动不开放,连调试工具都跑不了
- **需要多显示器 + IDE 的工作**:不是性能问题,是**界面放不下**。一个 IDE 十几个面板,手机屏幕装不下
- **需要长时间独占资源**:编译三小时不能被打断,而手机是要接电话的
- **散热**:持续满载会让芯片降频,而台式机有风扇。**这是手机目前最真实的短板**

**共同的规律是:这些活的门槛不是"会不会写代码",是"要不要一台专门的机器。** 手机是一台通用设备,它什么都能干一点,但没有一样能做到极致。造大型软件恰恰需要极致。

**所以准确的表述是:**

> **手机能干 90% 的日常工程工作,干不了那 10% 需要重型机械的活。而那 10% 恰好是最不需要"随时随地"的——你造浏览器内核,不会在公交车上造。**

**这条分界线,和"手机 vs 电脑"无关,和"通用设备 vs 专用设备"有关。** 一台两万块的台式机也造不了 3A 游戏,那是集群的活。

## 六、它的短板,以及怎么补

诚实地说,Kai9000 有三个明确的限制:

| 限制 | 影响 | 补充方案 |
|---|---|---|
| 没有子 Agent | 不能并行处理多个任务,不能交叉验证 | 交给电脑上的 opencode |
| 工具调用上限 15 次(硬编码) | 复杂任务跑到一半会被截断 | 用 CLI 当"外挂执行器" |
| 非常驻进程 | 不会自己醒来,不能自动回复 | 用 APK 按钮做到"变相自动" |

### 6.1 用 Termux CLI 变相突破工具上限

15 次工具调用听起来不少,但真正复杂的任务很容易超。比如"扫描仓库全历史找敏感信息"这种事,步数根本数不清。

解法很直接:**在 Termux 里装 codex、Claude Code 这类 CLI 工具**。

```
Kai(15 次上限)
  ↓ 花 1 次调用
Termux 里的 CLI
  ↓ 不受此限制
执行任意多步任务
```

**Kai 只需要说"帮我把这件事交给 CLI 跑",然后把结果拿回来。** 工具上限被变相绕过了。

### 6.2 用飞书群做多平台 AI 总线

手机只是其中一块屏。我把电脑上的 AI、还有各种自动化服务,全部接到同一个飞书群里。

```
        飞书群(消息总线)
       ↙        ↓         ↘
   手机 Kai   电脑 AI    自动化服务
```

好处是:
- 手机和电脑能"接力"——手机上说一句,电脑上的 AI 接着做
- 任何一方有结果,其他方都能看到
- 电脑关机了也不影响手机继续工作

**电脑开着的时候,消息是秒回的;电脑关着的时候,手机可以随时接上。**

### 6.3 用 APK 做到"变相自动回复"

这一条最有意思,也最能体现"改变问题形状"的思路。

**问题**:Kai 本身没有"事件监听"的能力——它只在你打开它、给它指令时才工作。它不会自己发现"群里来消息了"。

(注意:这不是因为"后台会被杀"。开了自启动和电池无限制之后,它能长时间稳定运行。问题出在它没有内置的"监听某个消息源并主动响应"这个功能。)

**常规思路**:想办法让它常驻 → 撞墙(Android 权限模型不允许)。

**换一个问法**:既然"程序自动完成"做不到,那能不能让"人的动作"短到几乎无感?

于是就做了这个小 APK:

```
┌────────────────────────────┐
│  点一下 → 复制 → 打开Kai   │
│  ┌──────────────────────┐  │
│  │     打开 Kai         │  │
│  └──────────────────────┘  │
│  │     看群消息         │  │
│  │     看邮件           │  │
│  └──────────────────────┘  │
└────────────────────────────┘
```

点一下 → 常用指令进剪贴板 + Kai 跳到前台 → 长按粘贴 → 发送。

**全程不用打字。** 从"拿出手机、找到 App、手打指令"变成"点一下、粘一下"。

这不是真正的自动化,但它把成本降到了可以接受的程度。

## 七、把手机当 AI 宿主的真实体验

说完了能力,说体验。

### 7.1 先纠正三个常见的误解

在讲真实体验之前,我需要先澄清三件**大家都这么说、但实际不成立**的事。因为这三条误解,挡住了很多人尝试手机 AI。

**误解一:"手机后台会被杀,不能常驻。"**

这是最常听到的一条,也是最需要更新的。

实际做法是:在系统设置里给这个应用**开自启动 + 电池策略设为「无限制」**。做完这两步之后——

- 锁屏不影响它继续工作
- 不会因为"省电"被系统挂起
- **除非你主动划掉它,否则它一直在**

这不是理论。我这套东西已经连续工作了很多天,期间手机锁屏、开关网络、切换应用,都没有让任务中断过。

真正会发生的情况只有一种:**你手动把它干掉**。那属于"用户选择",不是"系统限制"。

**误解二:"手机上跑 AI 很耗电、会发烫。"**

这条的前提错了。

**模型根本不在手机本地跑。** 推理在云端,手机只负责发请求、收结果。这个负载比你刷十分钟短视频还轻。

对比一下:

| 场景 | GPU 占用 | 发热 |
|---|---|---|
| 玩大型 3D 游戏 | 满载 | 明显发烫 |
| 看高清视频 | 中等 | 微温 |
| **手机上跑 AI Agent** | **接近 0** | **没有** |

我持续跑了很多天任务,手机从未因为这个应用发烫过。

**顺便说一句,这个误解还有一个隐藏的好处**:正因为模型不在本地,手机的性能天花板不取决于手机,而取决于你连的那个模型。**一部三年前的手机,和最新的旗舰,在 AI 这件事上体验是一样的。**

**误解三:"手机输入不如电脑,只适合确认不适合构思。"**

恰恰相反——**手机的输入方式比电脑多。**

| 输入方式 | 电脑 | 手机 |
|---|---|---|
| 键盘 | ✅ | ✅ |
| 语音输入 | ⚠️ 需要装软件 | ✅ 系统自带,准确率很高 |
| 手写 | ❌ 需要数位板 | ✅ 屏幕直接写 |
| 拍照 OCR | ⚠️ 需要扫描仪 | ✅ 拍一张就能提取文字 |
| 分享菜单 | ❌ | ✅ 任何 App 里的内容一键送入 |
| 剪贴板接力 | 同设备才可 | ✅ 跨应用自由流转 |

举几个我实际用过的场景:

- 在工厂现场,拍一张设备铭牌,直接问它这是什么型号、什么参数
- 走路时想到一件事,语音说一句,它就记下来了
- 看到一份纸质文件,拍下来让它提取内容并整理
- 在别的 App 里看到一段文字,分享给它继续处理

**这些事在电脑上要么做不到,要么要额外设备。**

所以准确的表述不是"手机不如电脑",而是:**手机适合"随时随地capturing想法",电脑适合"坐下来长时间打磨"。它们是互补的,不是替代的。**

### 7.2 真正做不到的是什么

说完误解,说真正的边界。这三条是绕不过去的:

**1. 接收公网请求做不到。**

Webhook、回调地址、公网 API——这些需要"外面能主动找到你"。手机没有固定公网 IP,做不了。

这条是硬限制。任何需要"别人主动推给我"的服务,必须有个能长期在线的公网入口。

**2. 跨应用自动执行受限。**

Android 的权限模型越来越严。我实测过 8 种方式想让一个应用自动调用另一个应用,全部失败。

实测过的 8 种尝试全部失败,具体见第六节 6.3。这里只说结论:**能做到"点一下就完成",做不到"完全自动"。**

**3. 单个应用的能力上限。**

比如工具调用次数有硬编码上限、没有子 Agent。这是应用自身的设计,不是手机的限制——但既然你在用这个应用,它就是你面对的天花板。

好在这条有解:用 Termux 里的 CLI 工具当"外挂执行器",把复杂任务外包出去(详见 6.1)。

## 八、我的实际架构

经过一段时间摸索,现在的分工是这样的:

| 位置 | 角色 | 承担什么 | 成本 |
|---|---|---|---|
| **手机** | 指挥中心 + 常驻执行 | 随时查看、快速决策、完整开发流程、拍照识别、语音输入、定时轮询 | 0(现成硬件) |
| **电脑** | 重活 + 复杂思考 | 大仓库、多 Agent 并行、长时间调试 | 0(现成硬件) |
| **飞书群** | 消息总线 | 多设备消息互通、任务接力 | 0 |

**核心原则:要算力的放电脑(它能开沙箱),其余一切都能在手机上做——包括跑一整天的任务、定时轮询、长连接。**

关于"常驻"这件事要特别说明:**Termux 里的服务是可以长期维持长连接、定时轮询的。** 只要给应用开好自启动 + 电池无限制,手机就能像一台小服务器一样持续工作,而且不需要公网入口——因为它是主动出去拉,不是等人推进来。

**所以现阶段真正的支出只有一项:模型订阅。**

至于公网入口:如果你确实需要接收外部推送(比如平台回调),那才需要一台能长期在线的机器。**对大部分个人使用场景,这个需求根本不存在。**

## 九、如果你也想试试

给几条实操建议(都是我踩过坑之后总结的):

**1. 先解决"手机能干活"这件事。**
装 **F-Droid 版的 Termux**,确认它能执行命令。这一步不通,后面都是空的。

> ⚠️ 别从 Google Play 装。Play 上的 Termux 早已停止更新且不兼容新版本安卓插件,官方明确不推荐。F-Droid 版才是维护中的那个,插件（Termux:Boot、Termux:API）也只有 F-Droid 有。

**2. 把模型配置换成你能控制的。**
用任意 OpenAI 兼容端点都行,本地跑、免费池、付费 API 都可以。不要被单一厂商锁死。

**3. 从一件具体的小事开始。**
不要一上来就想"全自动"。先做一件"每天都要重复做、但很烦"的小事,让 AI 帮你省掉它。

**4. 接受"半自动"。**
Android 的权限模型不会给你"完全自动"。能把它做到"点一下就完成"已经是很大的改善,不要为了追求零操作而陷入无止境的折腾。

**5. 别急着买服务器。**
常驻任务手机上就能扛——给应用开自启动 + 电池无限制,定时轮询和长连接都能维持。**只有在需要「接收外部推送」时才需要公网入口**,那是另一类需求。先用手里的设备把流程跑通,确实撞到限制再说。

**6. 别急着买硬件。**
先用你手里现有的手机和电脑跑起来。等你真的撞到性能天花板了,再考虑投入。**大多数人的问题不是算力不够,是没开始用。**

## 十、最后

写这篇的目的是分享两个判断。

**第一,AI 的下一步不只是"更聪明",还有"更近"。**

当 AI 只能待在电脑里的时候,它是个工具;当它跟着你走进工厂、走上车、走进任何一个没有桌子的地方,它才开始变成伙伴。

Kai9000 是这个方向上比较早期的一个——在"手机上的通用 Agent"还没成为潮流的时候,它就已经能在手机上脱离电脑独立干活了。它有很多可以改进的地方(子 Agent、工具上限、常驻能力),而后来者的产品在很多方面已经做得比它更好。

但"第一个让我真的把 AI 带在身上"这件事,是它做到的。

**第二,这套东西没你想的那么贵。**

真正必须花钱的只有模型订阅。手机、电脑、消息群、开源工具,全都是现成的。而且随着芯片变强、开源模型变小,连订阅那笔钱最终也能省掉。

技术会迭代,今天的产品明天可能被替代。但把功劳说清楚是应该的:**是这个应用让我第一次真正把 AI 带在了身上。**

## 附:我在这套东西上做出来的两个工具

文章里提到"飞书群做消息总线"、"线索要有人审"。这两件事我后来都做成了能用的东西,顺便放在这里。

### LeadPulse Guard —— 线索监控

**解决的问题很具体:公域来的线索会丢。**

评论、广告表单、邮件,三个入口。平台的推送不可靠(实测有过当天 5 条线索只到 2 条的经历),所以它**同时跑兜底轮询**,把最坏情况压到 10 分钟以内。

但它的核心设计不是"自动回复",而是**拒绝执行**:

- 机器判断意图、生成草稿、判断该不该回
- **但发不发,永远由人决定**
- 审批走飞书卡片,三个按钮:发送 / 修改后发送 / 忽略

为什么这么设计?因为我在实际运营里见过三种典型的翻车:

1. **机器回环** —— AI 回复触发了自己的 webhook,两个 AI 互相回了一晚上
2. **礼貌死循环** —— 客户说"谢谢",AI 觉得该回,回完对方又说"不客气"
3. **一本正经地编** —— 客户问具体参数,模型编了一个听起来很专业的数字

这三个问题,靠提示词修不好。**靠"最后一步必须是人"才修得好。**

技术上是这样:**纯只读的安全入口 + 文件 spool 交接零网络边界 + 人在闭环里**。跑在我自己的手机和一台小机器上,没有为它多花一分钱。

> 官网:<https://leadpulseguard.com> ｜ 仓库:github.com/yangke821115/lead-pulse-guard

### RoboBridge —— 在做的下一块

这一条是**预告,不是成品**。仓库是私有的,还在写。

它要解决的问题是:我手上有 Kai(手机)、有 opencode(电脑)、有飞书群,它们各有各的账号和权限,但**彼此不通**。

现有的做法是用消息群当中转,人肉搬运。RoboBridge 想让它自动化——**让不同的 AI Agent 真正协作,而不是各自为战**。

这里有个容易被忽略的结构差异,它决定了整个设计:

**命令行类 Agent 可以直接用订阅账号登录,但聊天平台的 bot 只能走 API key。**

也就是说,同一个模型服务,在两种客户端里的接入身份完全不同。桥只能连两头的接口,**它变不出权限来**。

所以这个项目的定位很清楚:**它不生产额度,它让已有的东西连起来。** 谁有多少额度、能干什么,还是由各自的服务条款决定。

> **一句提醒**:平台政策在变,而且变得挺快。以前"订阅可以覆盖多个客户端"这种理解,现在不少厂商都在收紧——比如把不同产品线的用量合并计算。
>
> **所以别把任何"这样能省"当结论。** 桥的价值在于协作,不在于套利。政策一变,套利空间就没了,但协作的需求还在。
